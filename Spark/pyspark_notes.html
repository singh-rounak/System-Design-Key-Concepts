1  Spark Architecture — the mental model

Core idea: Spark is a driver that plans work, and executors that run it, coordinated by a cluster manager.

Driver plans & coordinates · Cluster Manager allocates resources · Executors do the actual work

Job → Stage → Task hierarchy

If you remember one sentence for architecture questions, it's this diagram.
TermWhat it is
ApplicationYour whole PySpark program, one SparkSession
JobTriggered by one action (e.g. .collect(), .count(), .write())
StageA chunk of a job with no shuffle inside it — a shuffle boundary creates a new stage
TaskSmallest unit of work — one task runs on one partition, on one core
TRAP"What happens if the driver dies?" → the whole application dies (single point of failure). If an executor dies, Spark just reschedules its tasks elsewhere using the DAG lineage to recompute lost partitions.

2  RDD vs DataFrame vs Dataset

PySpark has RDDs and DataFrames — there is no Python Dataset (Python is dynamically typed).

Why DataFrames are fast: Catalyst + Tungsten

Catalyst Optimizer rewrites your logical query into an efficient plan (predicate pushdown, constant folding, column pruning). Tungsten is the physical execution engine — manages memory off-heap (avoids JVM GC overhead) and generates optimized bytecode at runtime.

Lazy evaluation: transformations (filter, select, withColumn, join, groupBy) don't run immediately — they build the logical plan. Nothing executes until an action is called. This lets Catalyst see the whole chain and optimize it globally.

Transformations (lazy)Actions (trigger execution)
select, filter/where, withColumn, join, groupBy, orderBy, distinct, union show(), count(), collect(), take(), write.save(), foreach()

3  DataFrames — the workhorse

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("interview").getOrCreate()
df = spark.read.parquet("s3://bucket/orders/")

df2 = (
    df.filter(F.col("status") == "SHIPPED")
      .withColumn("order_month", F.month("order_date"))
      .groupBy("order_month")
      .agg(F.sum("amount").alias("total_amount"))
)

df2.explain(True)   # ALWAYS know this — shows the physical/logical plan

Things you should be able to say fluently: df.explain() shows you the plan Catalyst chose. Schema is either inferred (inferSchema=True, slower — extra read pass) or explicit via StructType (faster, safer, preferred in production). repartition(), coalesce(), cache(), persist() are the four you'll be grilled on next.

4  Partitions — Coalesce vs Repartition

A DataFrame is split into partitions; each partition is processed by one task on one core. How many partitions you have controls parallelism.

repartition(n) — full shuffle, even distribution

coalesce(n) — merges partitions, no full shuffle

coalesce()repartition()
ShuffleNo full shuffleFull shuffle
Can increase partitions?NoYes
Partition sizesUnevenEven
CostCheapExpensive
Typical useReducing partitions before writeIncreasing partitions / fixing skew / pre-join repartitioning
SAY THIS"Coalesce avoids a shuffle by merging existing partitions, so it's cheap but can leave data unevenly distributed. Repartition does a full shuffle to redistribute data evenly, so it's expensive but necessary when I need more partitions or need to fix skew."

5  Data Skew — the #1 real-world PySpark problem

What it is: some partitions hold way more data than others (a join/groupBy key is unevenly distributed — e.g. one customer_id owns 40% of orders). The task on that huge partition becomes the bottleneck — everything else finishes early and waits.

Detecting it: Spark UI shows one task in a stage taking dramatically longer than the rest (a long tail in task duration). Symptoms: job "hangs" near the end, executor OOM on specific tasks, uneven shuffle read sizes.

Fix 1 — Adaptive Query Execution (AQE, Spark 3.0+)

AQE re-optimizes the query plan at runtime using real statistics from completed stages, instead of relying only on the pre-execution estimate.

spark.conf.set("spark.sql.adaptive.enabled", "true")               # default on in 3.2+
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

AQE does three things automatically: (1) coalesces tiny post-shuffle partitions, (2) splits an oversized skewed partition so multiple tasks share the load, (3) switches join strategy (e.g. sort-merge → broadcast) if it discovers one side is actually small at runtime.

Fix 2 — Broadcast Joins

If one side of a join is small enough to fit in executor memory, send a full copy of it to every executor instead of shuffling both giant tables across the network.

from pyspark.sql.functions import broadcast
df_result = big_orders_df.join(broadcast(small_customers_df), "customer_id")

# auto-broadcast threshold (default 10MB)
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 100 * 1024 * 1024)  # 100MB

No shuffle on the big table → big speedup for star-schema joins (fact + small dimension table). Only works if the small side genuinely fits comfortably in executor memory. Set threshold to -1 to disable auto-broadcast for debugging.

Fix 3 — Salting (when both sides are large AND one key is skewed)

import pyspark.sql.functions as F
N = 10  # salt buckets

skewed_df = skewed_df.withColumn("salt", (F.rand() * N).cast("int")) \
                      .withColumn("salted_key", F.concat_ws("_", "join_key", "salt"))

salt_range = spark.range(N).withColumnRenamed("id", "salt")
other_df = other_df.crossJoin(salt_range) \
                    .withColumn("salted_key", F.concat_ws("_", "join_key", "salt"))

result = skewed_df.join(other_df, "salted_key")

6  Caching & Persistence

Because Spark is lazy, reusing a DataFrame across 3 actions recomputes it 3 times from scratch — walking the whole lineage — unless you cache it.

df_expensive = df.filter(...).join(other_df, "key").groupBy("region").agg(F.sum("amount"))

df_expensive.cache()          # shorthand for persist(MEMORY_AND_DISK)
df_expensive.count()          # ACTION — this is what materializes the cache

df_expensive.filter(F.col("region") == "US").show()     # reads from cache, fast
df_expensive.filter(F.col("region") == "EU").show()     # reads from cache, fast

df_expensive.unpersist()      # free memory when done
Storage LevelWhereNotes
MEMORY_ONLYRAM onlyFastest; recomputed if it doesn't fit
MEMORY_AND_DISKRAM, spills to diskDefault for .cache(); safer
MEMORY_ONLY_SERRAM, serializedSaves space, costs CPU to (de)serialize
DISK_ONLYDisk onlySlow but never OOMs
MEMORY_AND_DISK_2Same + replicated on 2 nodesFault tolerance at a memory cost

When to cache: the DataFrame is reused multiple times (iterative algorithms, multiple actions, ML training loops). Don't cache something touched only once — pure overhead.

TRAPDoes .cache() execute immediately? No — like all transformations it's lazy; nothing is cached until an action runs afterward.

7  Shuffles — why they're the enemy

A shuffle = data physically moves across the network between executors, writes to disk, then gets re-read. Triggered by groupBy(), non-broadcast join(), distinct(), repartition(), orderBy() — disk I/O + network I/O + serialization. Minimizing shuffles is the single biggest lever for performance.

8  Optimization Techniques — the interview checklist

Walk through these out loud as your "how would you optimize a slow Spark job" answer:

  1. Use DataFrame/SQL API over RDDs — gets you Catalyst + Tungsten for free.
  2. Predicate & column pruning — filter/select early so Catalyst can push filters down to the file scan.
  3. Use columnar file formats — Parquet/ORC over CSV/JSON: compressed, columnar reads, schema-aware, supports predicate pushdown.
  4. Partition data on disk by commonly-filtered columns (e.g. date) — enables partition pruning, skipping whole folders.
  5. Bucketing — pre-shuffle by a join/groupBy key at write time so future joins avoid a shuffle entirely.
  6. Broadcast joins for small dimension tables.
  7. Avoid UDFs when a built-in exists — they're a black box to Catalyst and pay a JVM↔Python serialization cost. Prefer Pandas (vectorized) UDFs if you must use Python.
  8. Cache reused intermediate results — but unpersist when done.
  9. Right-size partitions — target ~100–200MB per partition. Too few = underutilized cluster; too many = scheduling overhead dominates.
  10. Avoid collect() on large data — pulls everything to driver memory; use take(n) or write to storage instead.
  11. Handle skew — AQE, broadcast joins, salting.
  12. Tune spark.sql.shuffle.partitions (default 200) — often wrong for your data size; AQE's coalescePartitions mitigates this.
  13. Use explain() to verify the optimizer did what you expect.

9  Quick-fire interview Q&A

Q: Why is Spark faster than Hadoop MapReduce?
In-memory computation between stages (vs disk writes every step in MR), a DAG execution engine, and the Catalyst/Tungsten optimizer.
Q: repartition() vs partitionBy()?
repartition() redistributes in-memory partitions. partitionBy() is used at write time to organize output into folders on disk by column value (e.g. /year=2026/month=08/), enabling partition pruning on future reads.
Q: What causes OutOfMemory and how do you fix it?
Usually skew, too few partitions, collecting too much to the driver, or over-caching. Fixes: repartition/salt, avoid unnecessary collect(), tune executor memory, use MEMORY_AND_DISK instead of MEMORY_ONLY.
Q: What is lineage/DAG used for besides planning?
Fault tolerance — if an executor is lost, Spark recomputes only the lost partitions via lineage instead of restarting the whole job.
Q: groupBy().count() vs countDistinct() — which is heavier?
Both shuffle, but distinct counting on high-cardinality columns is heavier — consider approx_count_distinct when exactness isn't required.
Q: When would you avoid coalesce(1)?
When writing a large dataset — 1 task does all the write work serially, killing parallelism. Fine only for genuinely small outputs.

10  One-page cheat sheet

# Read
df = spark.read.schema(my_schema).parquet("path")   # explicit schema > inferSchema in prod
df.explain(True)                                     # inspect the plan

# Partitioning
df.repartition(200)                 # full shuffle, even sizes, can increase
df.repartition("customer_id")       # repartition BY column — co-locates keys before a join
df.coalesce(1)                      # cheap merge, decrease only, uneven sizes

# Broadcast join
from pyspark.sql.functions import broadcast
big.join(broadcast(small), "key")

# AQE (Spark 3.0+, default on in 3.2+)
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

# Caching
df.cache()                              # = persist(MEMORY_AND_DISK)
df.persist(StorageLevel.MEMORY_ONLY)
df.unpersist()

# Write with partitioning + bucketing
df.write.partitionBy("year", "month").parquet("path")
df.write.bucketBy(8, "customer_id").saveAsTable("bucketed_table")

# Vectorized (Pandas) UDF — prefer over row-at-a-time UDF
from pyspark.sql.functions import pandas_udf
@pandas_udf("double")
def add_tax(price: "pd.Series") -> "pd.Series":
    return price * 1.18
